# Hosting for health-system scientists and the complete FY2027 ICD-10-CM corpus

**Research date:** 2026-11-07. **Status:** recommendation and public-source verification, not deployment approval.

## Executive decision

**Recommended initial design:** a standalone Python MCP container on **Azure Container Apps in the institution's approved tenant**, with **private VNet/VPN reachability and Microsoft Entra authorization**, serving a versioned, immutable local SQLite catalog. Start with one approved desktop MCP client on a managed institutional device. Do not add a model service, a writable database service, arbitrary code execution, or PHI processing to this pilot. Azure explicitly supports custom Python MCP servers using Streamable HTTP in ordinary containers; its separate “dynamic sessions MCP” product is for sandboxed code execution and is not the appropriate product for this terminology server. [Azure hosting][azure-host]

**FY2027 is published and accessible.** CDC's release page links to its FY2027 directory, which contains both the complete code-description/order archive and the complete table-and-index archive, separately from the addenda. This investigation verified HTTP accessibility, ZIP member names, and XML root/version prefixes for the Tabular and all four indexes. It did **not** download either complete archive, verify all member CRCs, generate a database, or establish corpus-wide code counts. Publication is therefore **not a blocker**; full download, integrity checks, parsing, and reconciliation remain implementation gates. [CDC release page][cdc-files] [CDC FY2027 directory][cdc-2027] [Code archive][cdc-codes] [Table/index archive][cdc-tables]

### Scope and evidence discipline

- Parent-supplied project context, not independently re-inspected: Python 3.11+, official MCP SDK 1.30, stdio-only transport, generated read-only SQLite FTS5 catalogs, no PHI/model/cloud runtime, and only the April–September 2026 release implemented.
- Only public primary sources were researched. No cloud account was accessed, no infrastructure was provisioned, and no project source code or tests were read or changed.
- “Verified” below means supported by a cited primary page or explicitly described live HTTP observation. Proposed settings and acceptance gates are recommendations, not claims about an already working deployment.

## A. Hosting findings

### 1. Comparison for this particular server

| Option | Verified capabilities and constraints | Recommendation |
| --- | --- | --- |

Microsoft recommends a minimum of one replica for interactive MCP use. [Azure hosting][azure-host] | **First choice when the institution already approves Azure/Entra.** Keeps the existing Python/SQLite architecture rather than introducing a runtime port. |
| **Cloudflare Python Workers** | Python executes as Pyodide/CPython compiled to WebAssembly inside a V8 isolate. Supported packages are pure Python, PyEmscripten wheels, and packages supplied by Pyodide; this is not an ordinary Linux Python container. [Python runtime][cf-python] [Packages][cf-packages] | Viable research option, but **not a verified drop-in deployment** of this SDK/SQLite FTS5 application. | **Cloudflare Containers + Worker + Access** | Runs existing container images, with lifecycle/routing controlled by Worker/Durable Object code. ### 2. One practical initial Azure design

**Proposed request path**

```text
Managed institutional desktop MCP client
  -> institutional VPN / connected private network + private DNS
  -> HTTPS endpoint on an internal Container Apps environment
  -> Python Streamable HTTP /mcp resource server
       -> Entra-issued token validation + researcher authorization
       -> local, read-only versioned SQLite FTS5 artifacts
```

Recommended implementation boundaries:

1. **Add Streamable HTTP without removing stdio.** Run an ordinary standalone MCP container with a configured target port, for example 8080, and ingress transport `auto` or `http`. “Streamable HTTP” is the MCP transport inside the container, not a special Azure ingress setting. Use a separate `/healthz` endpoint for probes. [Azure hosting][azure-host] [Azure MCP security][azure-auth]
2. **Private environment, externally visible app within that private boundary.** Create the Container Apps **environment as internal**, then set the **app's ingress to external** so clients on the connected VNet can reach its internal load balancer. Counterintuitively, app-level `internal` ingress normally limits direct access to the same Container Apps environment, not all VPN/VNet clients. Environment-level HTTP route configurations can also affect exposure. Microsoft documents this exact two-setting distinction and the VNet-only configuration. [Ingress][azure-ingress]
3. **Use Entra as the authorization server and the Python MCP app as a protected resource.** Implement MCP discovery/challenges and token validation through the pinned SDK's supported resource-server integration and a vetted authentication/JWT library, not hand-written cryptography. Enforce researcher access and tool scopes in addition to token validity. This is the proposed initial auth boundary; do not treat a browser sign-in page as sufficient MCP authorization. [Entra MCP guidance][entra-mcp] [MCP authorization][mcp-auth]
4. **Build the catalog once, serve identical immutable copies.** Generate and verify the SQLite database in a controlled build step, package it with a source manifest in the container image, and open it read-only at runtime. Record database/source SHA-256 digests and the release identity in the artifact manifest. Use `mode=ro`; use `immutable=1` only when deployment guarantees the bytes cannot change under an open connection. SQLite warns that falsely asserting immutability can yield incorrect results or corruption errors. Replace the image/revision for updates instead of editing a live database. [SQLite URI semantics][sqlite-uri]
5. **Prefer stateless request handling.** Microsoft explicitly recommends Python `stateless_http=True` for stateless MCP security. For this lookup workload, prefer bounded JSON responses rather than depending on a long-lived stream or replica-local session state; verify the exact SDK 1.30 options and target-client behavior before implementation. Start with minimum one replica and a small bounded maximum, with capacity chosen after load tests. Each replica reads the same packaged catalog; do not add shared writable SQLite over a network file share. Ephemeral local writes disappear when a container restarts, so no critical runtime state should depend on them. [Azure MCP security][azure-auth] [Azure hosting][azure-host] [Storage][azure-storage]
6. **Operational controls are still required.** Recommend non-root execution, pinned image/dependencies, image scanning, restricted egress, no runtime source downloads, input/result-size limits, rate limits, a minimal health response, and logs containing operation/status/latency rather than prompts, tool arguments/results, tokens, or patient text. Keep artifact verification and scientist/client onboarding as explicit release checks. These are proposed controls under the institution's retained application/data/identity responsibilities. [Azure MCP security][azure-auth] [Shared responsibility][azure-shared]

The existing application's transport/auth integration and these controls have **not** been implemented or tested by this research task.

### 3. Entra and MCP interoperability: what must actually be proved

**Verified:** Container Apps documents built-in Entra authentication with `Return401`, an exposed API scope, and MCP clients supplying a bearer token. Its example includes a manually acquired development token. That proves a documented bearer-token path; it does **not** prove that enabling Easy Auth alone implements complete OAuth discovery, client registration, consent, refresh, and authorization for every MCP client. [Azure MCP security][azure-auth]

**Verified:** MCP's current authorization specification uses OAuth resource-server semantics, protected-resource metadata (RFC 9728), authorization-server discovery, bearer access tokens, and resource/audience binding. A client's registration and supported authorization flow matter. [MCP authorization][mcp-auth]

**Verified current Entra guidance:** for native MCP resource matching, set `api.requestedAccessTokenVersion` to `2`; register an HTTPS Application ID URI exactly matching the canonical MCP URL; expose delegated scopes; publish PRM identifying the tenant's v2 issuer; validate signature, issuer, tenant, audience, expiry, and caller permissions. **For Entra v2 tokens, the expected `aud` is the resource application's client-ID GUID, not simply the endpoint's HTTPS URL.** The canonical URL/resource match and token-audience validation are related but different checks. [Entra MCP guidance][entra-mcp]

**Verified client constraint:** Microsoft's MCP auth guidance says Entra does not support Dynamic Client Registration and recommends preauthorizing known client applications when possible. Do not promise arbitrary consumer MCP clients will work without client registration/configuration. [Microsoft MCP client guidance][appservice-mcp-auth]

**Recommended pilot acceptance gates:**

- Select one institutional desktop MCP client first; VS Code desktop is a documented bearer-header client, but its end-to-end institutional OAuth configuration still needs a real test. Pre-register/preauthorize the actual client and redirect URIs; require delegated least-privilege lookup scopes and approved researcher access. [Azure MCP security][azure-auth] [Microsoft MCP client guidance][appservice-mcp-auth]
- Verify unauthenticated access gets **401 plus a usable `WWW-Authenticate` metadata pointer**, not an HTML login/302 loop. The metadata endpoint must be discoverable without already holding a token. Complete interactive login, consent, token acquisition, expiration/refresh, and access revocation from the actual client. [Entra MCP guidance][entra-mcp] [MCP authorization][mcp-auth]
- Reject wrong-tenant, wrong-audience, expired, unassigned/unauthorized, and insufficient-scope requests. Do not accept a Microsoft Graph token as a token for this MCP resource. [Entra MCP guidance][entra-mcp] [MCP authorization][mcp-auth]
- If platform Easy Auth is added, verify it preserves the application's intended discovery/challenge behavior and correct audience policy; do not assume App Service's preview PRM setting exists on Container Apps. The cited PRM feature belongs to **App Service**, whereas Container Apps' cited walkthrough demonstrates bearer-token authentication. [App Service MCP auth][appservice-mcp-auth] [Azure MCP security][azure-auth]
- For browser clients, allow only approved CORS origins and the actual MCP request/response headers needed by those clients. Desktop requests are not governed by browser CORS; CORS does not create network reachability. [Azure MCP security][azure-auth] [Ingress][azure-ingress]

The older Container Apps walkthrough's `api://APP_ID` manual-token example and newer native MCP canonical-HTTPS-resource guidance are **not interchangeable configurations**. Choose and test the intended client flow rather than combining examples mechanically. [Azure MCP security][azure-auth] [Entra MCP guidance][entra-mcp]

### 4. Private/VPN clients versus Internet-hosted clients

An internal environment has no public endpoint. A desktop client can reach it only if its execution host has the required private route and DNS, for example over institutionally connected VPN/VNet networking. **A user's browser being on VPN does not make a vendor-hosted MCP connector's servers part of that network.** This is the network consequence of the documented private ingress boundary, not a verified capability of any particular AI product. [Ingress][azure-ingress]

Therefore, launch with an approved client actually executing on the managed/private-network host. If scientists require a cloud-hosted assistant, first verify that product's supported private connectivity or approved gateway. Otherwise it needs an institution-approved Internet-reachable endpoint, with working MCP OAuth and authorization; that is a **separate exposure decision**, not “turn on public ingress because the client cannot connect.” Azure also supports Private Link with public network access disabled, but that is an alternative institutional networking design, not an extra requirement for the recommended internal-environment pilot. [Ingress][azure-ingress] [Private endpoints][azure-private]

For a separate Internet-accessible **terminology-only** pilot, recommend the same immutable application and researcher authentication, explicit “no patient data” use limits, minimal logging, and a separate reviewed exposure configuration. “Public” describes endpoint reachability, not permission to send clinical notes or a requirement to permit anonymous use.

### 5. Cloudflare auth is better than “put Access in front,” but still needs integration

Cloudflare's current Managed OAuth documentation explicitly addresses non-browser clients: ordinary Access browser redirects are not enough; Managed OAuth returns a discoverable 401 flow and issues OAuth access tokens. It supports self-hosted applications, MCP server applications, and MCP portals. For an MCP server application, the server must validate the Access assertion in `Cf-Access-Jwt-Assertion`. Managed OAuth tokens presented by clients are opaque; Cloudflare resolves them and forwards a signed assertion to the origin. Do not decode those opaque tokens as JWTs. [Managed OAuth][cf-managed-oauth]

Cloudflare also documents a Workers OAuth Provider pattern with distinct authorization/resource servers. Either design is an actual auth integration; neither follows automatically from enabling a generic browser Access policy. Do not enable Managed OAuth over an existing OAuth implementation that depends on its own challenges without checking the documented interaction. [Workers MCP authorization][cf-mcp-auth] [Managed OAuth][cf-managed-oauth]

This narrows the objection to Cloudflare: it is **not** that it lacks Python, containers, or MCP OAuth. The issue is the extra runtime/integration validation and institutional governance relative to an already suitable approved Azure tenant.

### 6. No automatic HIPAA compliance; keep PHI out of this pilot

**Azure verified:** Microsoft offers a HIPAA BAA through applicable Product Terms/DPA for in-scope services and explicitly says a BAA or use of Azure does not make a customer's application compliant. Its public scope page points to the Service Trust Portal's current compliance-offerings appendices for service-level scope. This investigation did not access that portal or confirm this institution's agreement, exact services/SKUs, regions, or approvals. **Container Apps and all supporting services must be checked under the applicable current scope before any PHI use is considered.** [Azure HIPAA][azure-hipaa] [Azure audit-scope directory][azure-scope]

**Cloudflare verified:** its current HIPAA FAQ offers BAAs to Enterprise-level customers, requires formal execution before PHI passes through Cloudflare, and lists Workers, Access, Durable Objects, R2 and other services in its AoC scope. **Containers is not explicitly named in the inspected public list.** Do not infer Containers eligibility from Workers coverage; get contract/service-specific confirmation. [Cloudflare HIPAA][cf-hipaa]

**Recommendation:** treat a PHI-capable version as a separate project/security review: approved contracts and service scope, complete data-flow inventory, client/model-provider approval, retention and logging controls, minimum necessary access, incident response, and institutional privacy/security sign-off. Identity, data, application configuration, and access controls remain customer responsibilities even on managed cloud infrastructure. [Shared responsibility][azure-shared] [Azure HIPAA][azure-hipaa]

The absence of a server-side model does not establish that patient information is safe: tool inputs, client conversation history, results, traces, and future scoring inputs would all need review. For this pilot, recommend public terminology plus wholly synthetic draft cases only, no patient identifiers or copied clinical text, no synthetic “gold standard” claim before clinician/coder review, and no scoring tool enabled merely because hosting/auth is ready. These are project safety boundaries, not provider compliance guarantees.

### 3. Counts, checksums, and remaining verification gates

**Not found in the inspected release page, directory listing, or ZIP metadata:** an official corpus-wide billable-code total, all-code/category count, index-entry counts, or published SHA-256 archive hashes. Do not substitute a third-party count, an addenda count, a previous-year count, an ETag, or a fabricated checksum. ZIP-declared CRC32 values above are source metadata useful for later member integrity checks, **not** cryptographic provenance digests and **not** CRC values recomputed by this investigation. [CDC release page][cdc-files] [CDC FY2027 directory][cdc-2027] [Code archive][cdc-codes] [Table/index archive][cdc-tables]

**Recommended subsequent build gate, after scope/download approval:**

1. Download **both complete archives** from the exact URLs above; record final URL, retrieval time, HTTP status, byte size, Last-Modified/ETag when present, and locally calculated SHA-256. A locally calculated digest is a reproducibility anchor, not a claim that CDC published that digest.
2. Test ZIP integrity, enforce safe extraction paths, and require the complete code text, complete order text, Tabular XML, all four index XML files, and appropriate schema files. Retain actual original member names.
3. Parse every XML in full, require the expected root and version `2027`, and fail closed on missing/truncated files or unexpected release identity. Validate against the provided schemas where compatible with the parser and document any deliberate exception.
4. Derive and record clearly defined counts separately: billable/valid codes, nonbillable hierarchy nodes, Tabular nodes, order rows, and each index's entries. Reconcile code/order/Tabular overlap according to their documented semantics; do not equate every intermediate index reference with a billable code.
5. Compare against April 2026 for additions, deletions, and changed rules as a consistency check. Use addenda for corroboration, never as the primary full-corpus input.
6. Build a separate FY2027 catalog with its manifest and service-date interval. Only then run lookup/evidence regression tests and draft synthetic-case evaluation, with later clinician/coder adjudication before describing cases as validated.

**Outstanding blockers:** no public-source publication/access blocker was found. Implementation is still blocked on full-file integrity/parsing/reconciliation, approved evaluation scope, and—separately—hosting/client/auth/institutional approvals. No deployment, corpus download, or accuracy/scoring claim is authorized or implied by this report.

After the research task, the parent agent downloaded both full archives directly
from the cited CDC HTTPS URLs, without overwriting any existing catalog. Files and
per-member provenance manifests are under `data/releases/2027/sources/` (ignored).
The standalone Python certificate lookup initially failed; the successful retry used
the installed `certifi` CA bundle with certificate verification still enabled.

- All archive-member CRC checks passed. All five required XML files parsed fully
  with `defusedxml` and had the expected root and version `2027`.
- The complete code file contains **74,879** unique code rows. The order file contains
  **98,403** unique rows: **74,879** assignable codes and **23,524** headers. Its
  assignable code set equals the complete-code file's set. These are locally derived
  counts, not independently published CDC totals.
- The Tabular XML contains **47,025** `diag` elements. The four index XML files contain
  **81,642**, **8,090**, **7,436**, and **1,940** main/subterm entries respectively
  (diseases, external causes, drugs, neoplasms).

  `/usr/bin/shasum -a 256`:
